1# Automatic Prefix Caching
2
3Prefix caching kv-cache blocks is a popular optimization in LLM inference to avoid redundant prompt computations. The core idea is simple – we cache the kv-cache blocks of processed requests, and reuse these blocks when a new request comes in with the same prefix as previous requests. Since prefix caching is almost a free lunch and won’t change model outputs, it has been widely used by many public endpoints (e.g., OpenAI, Anthropic, etc.) and most open source LLM inference frameworks (e.g., SGLang).
4
5While there are many ways to implement prefix caching, vLLM chooses a hash-based approach. Specifically, we hash each kv-cache block by the tokens in the block and the tokens in the prefix before the block:
6
7```text
8 Block 1 Block 2 Block 3
9 [A gentle breeze stirred] [the leaves as children] [laughed in the distance]
10Block 1: |<--- block tokens ---->|
11Block 2: |<------- prefix ------>| |<--- block tokens --->|
12Block 3: |<------------------ prefix -------------------->| |<--- block tokens ---->|
13```
14
15In the example above, the KV cache in the first block can be uniquely identified with the token “A gentle breeze stirred”. The third block can be uniquely identified with the tokens in the block “laughed in the distance”, along with the prefix tokens “A gentle breeze stirred the leaves as children”. Therefore, we can build the block hash of `hash(tuple[components])`, where components are:
16
17* Parent hash value: The hash value of the parent hash block.
18* Block tokens: A tuple of tokens in this block. The reason to include the exact tokens is to reduce potential hash value collision.
19* Extra hashes: Other values required to make this block unique, such as LoRA IDs, multi-modality input hashes (see the example below), and cache salts to isolate caches in multi-tenant environments.
20
21!!! note "Note 1"
22 We only cache full blocks.
23
24!!! note "Note 2"
25 In previous versions, the hash key was not guaranteed to be collision-free. As of v0.11, the default hashing algorithm is `sha256`, which addresses collision risks.
26
27 For `vllm serve`, you can control the hashing algorithm via `--prefix-caching-hash-algo`:
28 - `sha256` (default): Uses Python's `pickle` for serialization. Hashes may not be reproducible across different Python or vLLM versions.
29 - `sha256_cbor`: Uses `cbor2` for serialization, providing a reproducible, cross-language compatible hash. This is recommended for deterministic caching across environments.
30 - `xxhash`: Uses Pickle serialization with xxHash (128-bit) for faster, non-cryptographic hashing. Requires the optional `xxhash` package. IMPORTANT: Use of a hashing algorithm that is not considered cryptographically secure theoretically increases the risk of hash collisions, which can cause undefined behavior or even leak private information in multi-tenant environments. Even if collisions are still very unlikely, it is important to consider your security risk tolerance against the performance benefits before turning this on.
31 - `xxhash_cbor` combines canonical CBOR serialization with xxHash for reproducible hashing. Requires the optional `xxhash` package.
32
33**A hashing example with multi-modality inputs**
34In this example, we illustrate how prefix caching works with multi-modality inputs (e.g., images). Assuming we have a request with the following messages:
35
36```text
37messages = [
38 {"role": "user",
39 "content": [
40 {"type": "text",
41 "text": "What's in this image?"
42 },
43 {"type": "image_url",
44 "image_url": {"url": image_url},
45 },
46 ]},
47]
48```
49
50It will become the following prompt:
51
52```text
53Prompt:
54 <s>[INST]What's in this image?\n[IMG][/INST]
55
56Tokenized prompt:
57 [1, 3, 7493, 1681, 1294, 1593, 3937, 9551, 10, 4]
58
59Prompt with placeholders (<P>):
60 [1, 3, 7493, 1681, 1294, 1593, 3937, 9551, <P>, <P>, ..., <P>, 4]
61```
62
63As we can see, after the tokenization, the `[IMG]` will be replaced by a sequence of placeholder tokens, and these placeholders will be replaced by image embeddings during prefill. The challenge for prefix caching to support this case is we need to differentiate images from the placeholders. To address this problem, we encode the image hash generated by the frontend image processor. For example, the hash of the blocks in the above prompt would be (assuming block size 16, and we have 41 placeholder tokens):
64
65```text
66Block 0
67 Parent hash: None
68 Token IDs: 1, 3, 7493, 1681, 1294, 1593, 3937, 9551, <p>, ..., <p>
69 Extra hash: <image hash>
70Block 1
71 Parent hash: Block 0 hash
72 Token IDs: <p>, ..., <p>
73 Extra hash: <image hash>
74Block 2
75 Parent hash: Block 1 hash
76 Token IDs: <p>, ..., <p>
77 Extra hash: <image hash>
78Block 3
79 Parent hash: Block 2 hash
80 Token IDs: <p>, ..., <p>, 4
81 Extra hash: <image hash>
82```
83
84In the rest of this document, we first introduce the data structure used for prefix caching in vLLM v1, followed by the prefix caching workflow of major KV cache operators (e.g., allocate, append, free, eviction). Finally, we use an example to illustrate the end to end prefix caching workflow.
85
86**Cache Isolation for Security**
87To improve privacy in shared environments, vLLM supports isolating prefix cache reuse through optional per-request salting. By including a `cache_salt` in the request, this value is injected into the hash of the first block, ensuring that only requests with the same salt can reuse cached KV blocks. This prevents timing-based attacks where an adversary could infer cached content by observing latency differences. This offers protection without compromising performance.
88
89```json
90{
91 "messages": [
92 {"role": "system", "content": "You are a helpful assistant."},
93 {"role": "user", "content": "Here is a document with details about the world series: ..."},
94 {"role": "user", "content": "Who won the world series in 2020?"}
95 ],
96 "cache_salt": "your-cache-salt"
97}
98```
99
100With this setup, cache sharing is limited to users or requests that explicitly agree on a common salt, enabling cache reuse within a trust group while isolating others.
101
102## Data Structure
103
104The prefix caching in vLLM v1 is implemented in the KV cache manager. The basic building block is the “Block” data class (simplified):
105
106```python
107class KVCacheBlock:
108 # The block ID (immutable)
109 block_id: int
110 # The block hash (will be assigned when the block is full,
111 # and will be reset when the block is evicted).
112 block_hash: BlockHash
113 # The number of requests using this block now.
114 ref_cnt: int
115
116 # The pointers to form a doubly linked list for the free queue.
117 prev_free_block: "KVCacheBlock | None" = None
118 next_free_block: "KVCacheBlock | None" = None
119```
120
121There are two design points to highlight:
122
1231. We allocate all KVCacheBlock when initializing the KV cache manager to be a block pool. This avoids Python object creation overheads and can easily track all blocks all the time.
1242. We introduce doubly linked list pointers directly in the KVCacheBlock, so that we could construct a free queue directly. This gives us two benefits:
125 1. We could have O(1) complexity moving elements in the middle to the tail.
126 2. We could avoid introducing another Python queue (e.g., `deque`) which has a wrapper to the elements.
127
128As a result, we will have the following components when the KV cache manager is initialized:
129
130![Component Overview](../assets/design/prefix_caching/overview.png)
131
132* Block Pool: A list of KVCacheBlock.
133* Free Block Queue: Only store the pointers of head and tail blocks for manipulations.
134* Cache blocks: Mapping from hash key to block IDs.
135* Request blocks: Mapping from request ID to allocated block IDs.
136
137## Operations
138
139### Block Allocation
140
141**New request:** Workflow for the scheduler to schedule a new request with KV cache block allocation:
142
1431. The scheduler calls `kv_cache_manager.get_computed_blocks()` to get a sequence of blocks that have already been computed. This is done by hashing the prompt tokens in the request and looking up cache blocks.
1442. The scheduler calls `kv_cache_manager.allocate_slots()`. It does the following steps:
145 1. Compute the number of new required blocks, and return if there are no sufficient blocks to allocate.
146 2. “Touch” the computed blocks. It increases the reference count of the computed block by one, and removes the block from the free queue if the block wasn’t used by other requests. This is to avoid these computed blocks being evicted. See the example in the next section for illustration.
147 3. Allocate new blocks by popping the heads of the free queue. If the head block is a cached block, this also “evicts” the block so that no other requests can reuse it anymore from now on.
148 4. If an allocated block is already full of tokens, we immediately add it to the cache block, so that the block can be reused by other requests in the same batch.
149
150**Running request:** Workflow for the scheduler to schedule a running request with KV cache block allocation:
151
1521. The scheduler calls `kv_cache_manager.allocate_slots()`. It does the following steps:
153 1. Compute the number of new required blocks, and return if there are no sufficient blocks to allocate.
154 2. Allocate new blocks by popping the heads of the free queue. If the head block is a cached block, this also “evicts” the block so that no other requests can reuse it anymore from now on.
155 3. Append token IDs to the slots in existing blocks as well as the new blocks. If a block is full, we add it to the cache block to cache it.
156
157**Duplicated blocks**
158Assuming block size is 4 and you send a request (Request 1\) with prompt ABCDEF and decoding length 3:
159
160```text
161Prompt: [A, B, C, D, E, F]
162Output: [G, H, I]
163
164Time 0:
165 Tokens: [A, B, C, D, E, F, G]
166 Block Table: [0 (ABCD), 1 (EFG)]
167 Cache Blocks: 0
168Time 1:
169 Tokens: [A, B, C, D, E, F, G, H]
170 Block Table: [0 (ABCD), 1 (EFGH)]
171 Cache Blocks: 0, 1
172Time 2:
173 Tokens: [A, B, C, D, E, F, G, H, I]
174 Block Table: [0 (ABCD), 1 (EFGH), 2 (I)]
175 Cache Blocks: 0, 1
176```
177
178Now block 0 and block 1 are cached, and we send the same request again (Request 2\) with greedy sampling, so that it will produce exactly the same outputs as the Request 1:
179
180```text
181Prompt: [A, B, C, D, E, F]
182Output: [G, H, I]
183
184Time 0:
185 Tokens: [A, B, C, D, E, F, G]
186 Block Table: [0 (ABCD), 3 (EFG)]
187 Cache Blocks: 0, 1
188Time 1:
189 Tokens: [A, B, C, D, E, F, G, H]
190 Block Table: [0 (ABCD), 3 (EFGH)]
191 Cache Blocks: 0, 1, 3
192```
193
194As can be seen, block 3 is a new full block and is cached. However, it is redundant as block 1, meaning that we cached the same block twice. In v0, when detecting block 3 is duplicated, we free block 3 and let Request 2 use block 1 instead, so its block table becomes `[0, 1]` in Time 1. However, the block table in vLLM v1 is append-only, meaning that changing the block table from `[0, 3]` to `[0, 1]` is not allowed. As a result, we will have duplicated blocks for the hash key E-H. This duplication will be eliminated when the request is freed.
195
196### Free
197
198When a request is finished, we free all its blocks if no other requests are using them (reference count = 0). In this example, we free request 1 and block 2, 3, 4, 8 associated with it. We can see that the freed blocks are added to the tail of the free queue in the *reverse* order. This is because the last block of a request must hash more tokens and is less likely to be reused by other requests. As a result, it should be evicted first.
199
200![Free queue after a request is freed](../assets/design/prefix_caching/free.png)
201
202### Eviction (LRU)
203
204When the head block (least recently used block) of the free queue is cached, we have to evict the block to prevent it from being used by other requests. Specifically, eviction involves the following steps:
205
2061. Pop the block from the head of the free queue. This is the LRU block to be evicted.
2072. Remove the block ID from the cache block.
2083. Remove the block hash.

210## Example
211
212In this example, we assume the block size is 4 (each block can cache 4 tokens), and we have 10 blocks in the KV-cache manager in total.
213
214**Time 1: The cache is empty and a new request comes in.** We allocate 4 blocks. 3 of them are already full and cached. The fourth block is partially full with 3 of 4 tokens.
215
216![Example Time 1](../assets/design/prefix_caching/example-time-1.png)
217
218**Time 2: Request 0 makes the block 3 full and asks for a new block to keep decoding.** We cache block 3 and allocate block 4.
219
220![Example Time 2](../assets/design/prefix_caching/example-time-3.png)
221
222**Time 3: Request 1 comes in with the 14 prompt tokens, where the first 10 tokens are the same as request 0.** We can see that only the first 2 blocks (8 tokens) hit the cache, because the 3rd block only matches 2 of 4 tokens.
223
224![Example Time 3](../assets/design/prefix_caching/example-time-4.png)
225
226**Time 4: Request 0 is finished and free.** Blocks 2, 3 and 4 are added to the free queue in the reverse order (but block 2 and 3 are still cached). Block 0 and 1 are not added to the free queue because they are being used by Request 1.
227
228![Example Time 4](../assets/design/prefix_caching/example-time-5.png)
229
230**Time 5: Request 1 is finished and free.**
231
232![Example Time 5](../assets/design/prefix_caching/example-time-6.png)
233
234**Time 6: Request 2 comes in with the 29 prompt tokens, where the first 12 tokens are the same as request 0\.** Note that even the block order in the free queue was `7 - 8 - 9 - 4 - 3 - 2 - 6 - 5 - 1 - 0`, the cache hit blocks (i.e., 0, 1, 2) are touched and removed from the queue before allocation, so the free queue becomes `7 - 8 - 9 - 4 - 3 - 6 - 5`. As a result, the allocated blocks are 0 (cached), 1 (cached), 2 (cached), 7, 8, 9, 4, 3 (evicted).
