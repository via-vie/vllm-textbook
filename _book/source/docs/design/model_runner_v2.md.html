1# Model Runner V2 Design Document
2
3## Introduction
4
5Since vLLM V1 was first implemented, we discovered several fundamental design mistakes and accumulated significant technical debt. Many features were bolted on that were not considered in the original design. We also gained valuable insights into sampling techniques (for example, Gumbel-max sampling), tools (for example, Triton), and CUDA features (for example, UVA). With this knowledge, we implemented Model Runner V2 (MRV2) from first principles to be cleaner, more efficient, and more modular.
6
7In hindsight, many of V1's design choices were suboptimal. While MRV2 is not yet feature-complete, not rigorously tested, and still has open design decisions, we believe it is a substantial improvement over V1.
8
9This document describes the design of MRV2.
10
11## 1. Persistent Batch
12
13One significant source of friction in V1 is its persistent batch implementation.
14
15### Background
16
17V1 introduced persistent batches to minimize CPU overhead during input preparation. When requests are scheduled for a step, the model runner must construct contiguous input tensors (for example, block tables and per-request temperature values) to feed into the model. Building these tensors from scratch each step is often very slow in Python, especially for large tensors like block tables.
18
19The persistent batch optimization exploits the fact that request batches in consecutive steps are mostly identical. Only a few requests (if any) join or finish per step. By maintaining persistent state tensors and applying incremental diffs instead of reconstructing inputs from scratch, CPU overhead can be reduced significantly.
20
21### Problems with V1's Approach
22
23While efficient, V1's persistent batch design introduced unnecessary complexity due to coupling persistent state with input tensors. V1 uses persistent state tensors directly as model and sampler inputs, which imposes strict layout and ordering requirements. When requests join or finish, this often requires complex tensor-wide reordering rather than simple row insertion/removal.
24
25V1 also had to maintain `CachedRequestState`, a redundant backup copy of request state, because rows in persistent tensors can be overwritten while requests are still active.
26
27The result is complex bookkeeping that becomes more difficult under async scheduling.
28
29![Persistent Batch in V1](../assets/design/model_runner_v2/persistent_batch_v1.png)
30
31### MRV2's Solution
32
33MRV2 decouples persistent state tensors from per-step input tensors. Given request ordering for the step (usually determined by the attention backend), MRV2 gathers input tensors from persistent state.
34
351. Pre-allocate a fixed-size tensor with `max_num_reqs` rows (1024 by default on most platforms).
362. Assign each request a permanent row for its active lifetime (until finish or preemption).
373. Treat preemption as completion. On resume, re-add request data as fresh state.
38
39This removes the need for `CachedRequestState` and simplifies bookkeeping. Large state tensors are mostly stored on GPU memory, so gather runs in parallel on the GPU with low overhead.
40
41![Persistent Batch in MRV2](../assets/design/model_runner_v2/persistent_batch_mrv2.png)
42
43## 2. Async-First
44
45vLLM now relies heavily on asynchronous scheduling. The scheduler and worker prepare inputs for step `N+1` while the GPU executes step `N`, overlapping CPU and GPU work to maximize utilization.
46
47V1 was not originally designed with async scheduling in mind, and support required retrofitted behavior and hacks. MRV2 instead assumes the core model execution loop is a CUDA stream with no CPU synchronization points. CPU entrypoints queue work onto the stream.
48
49![Async execution timeline](../assets/design/model_runner_v2/async_sched.png)
50
51## 3. Removing Async Barrier
52
53A key requirement for async execution is that CPU operations remain non-blocking. Both explicit sync (for example, `torch.accelerator.synchronize`) and implicit sync (for example, unpinned `.to("cuda")`) must be avoided.
54
55However, async execution can introduce race conditions when CPU and GPU concurrently touch the same memory.
56
57Example (unsafe):
58
59```python
60class ModelRunner:
61 def __init__(self, ...):
62 # Pinned buffer
63 self.states = torch.zeros(
64 max_num_reqs, dtype=torch.int32, device="cpu", pin_memory=True
65 )
66
67 def execute_step(self, ...):
68 self.states[req_idx] = new_req.data
69 states = self.states.to("cuda", non_blocking=True)
70```
71
72The CPU may modify `self.states` while GPU is still reading from it via async copy.
73
74V1 addresses this with an async barrier around critical sections. That avoids races but has drawbacks:
75
761. Easy to miss protected buffers (bug-prone).
772. Inflexible organization (all CPU work must stay inside barrier).
783. Potentially less overlap due to synchronization.
79
80![Race condition with shared CPU buffer](../assets/design/model_runner_v2/async_race_condition.png)
81
82### MRV2's Solution: Eliminate the Race
83
84MRV2 separates persistent CPU state from the copied tensor:
85
86```python
87class ModelRunner:
88 def __init__(self, ...):
89 # Not pinned
90 self.states = torch.zeros(
91 max_num_reqs, dtype=torch.int32, device="cpu", pin_memory=False
92 )
93
94 def execute_step(self, ...):
95 self.states[req_idx] = new_req.data
96 tmp_states = self.states.pin_memory()
97 states = tmp_states.to("cuda", non_blocking=True)
98```
99
100Now CPU writes to `self.states` while GPU reads from `tmp_states`, eliminating the race without explicit synchronization.
101
102![No race with temporary pinned copy](../assets/design/model_runner_v2/async_no_race_condition.png)

104## 4. StagedWriteTensor
105
106For large tensors like block tables, MRV2 avoids full CPU-to-GPU copies each step by using `StagedWriteTensor`:
107
1081. Keep the base tensor on GPU.
1092. Stage diffs on CPU.
1103. Pack diffs into contiguous buffers.
1114. Copy packed diffs to GPU.
1125. Launch one kernel to apply diffs.
113
114Example usage:
115
116```python
117# Initialize state on GPU
118state = StagedWriteTensor(size=(1024, 1000), dtype=torch.int32, device="cuda")
119
120# Write [3, 1, 2] into row 2, starting at index 3
121state.stage_write(row=2, start=3, value=[3, 1, 2])
122
123# Write [-1, -2, -5] into row 0, starting at index 1
124state.stage_write(row=0, start=1, value=[-1, -2, -5])
125
126# Apply staged changes
127state.apply_write()
128```
129
130This supports ragged updates with no CPU-GPU synchronization and minimal kernel launches. It is especially useful for block tables and mixed CPU/GPU-written states such as `num_computed_tokens`.
131
132## 5. GPU-Native Input Metadata Preparation and Output Processing
133
134MRV2 uses Triton kernels to prepare inputs such as `input_ids`, `positions`, `query_start_loc`, and `seq_lens`.
135
136Benefits:
137
1381. Better async behavior: GPU can derive values (for example with speculative decoding) that CPU may not know yet.
1392. Lower CPU overhead: input prep is very cheap on GPU and avoids Python bottlenecks.
140
141### Universal Virtual Addressing (UVA)
142
143MRV2 uses UVA in some paths to let GPU kernels access large CPU-resident tensors directly (for example `prefill_token_ids`) without duplicating those tensors into GPU memory.
144
145## 6. Triton-Native Sampler
146
147MRV2 reimplements sampling mostly in Triton for better numeric/memory control and optimization.
148
149### Gumbel Sampling Kernel
150
151MRV2 introduces a Triton Gumbel sampling kernel that avoids explicit softmax materialization and uses stateless in-kernel RNG from seed input.
152
153### Efficient Top-K Logprobs
154
155V1 materializes full-vocabulary logprobs before top-k. MRV2 identifies top-k tokens from logits first, then computes logprobs only for selected tokens. This reduces peak GPU memory usage.
156
157### Memory-Efficient Prompt Logprobs
158
159MRV2 supports finer-grained chunking, including chunking inside a single prompt, to avoid memory spikes on long prompts.
160
161### Better Compatibility with Speculative Decoding
162
163Instead of expanding per-request sampling states to match per-logit shapes, MRV2 uses indirection (`idx_mapping`) inside kernels to map each logits vector to the right request state. This simplifies support for complex sampling parameters and logits processors.
164
165## 7. Modularity
166
167MRV2 emphasizes modularity. Compared to V1's large, entangled `gpu_model_runner.py`, MRV2 splits feature logic across dedicated files (for example, `mrope_utils.py`, `penalties.py`, and many others).
168
169It also consolidates model inputs into an `InputBatch` class and reduces direct model-runner attribute coupling.
170
171## 8. No Abuse of `dummy_run`
172
173In V1, `dummy_run` handled too many responsibilities:
174
175- Initial memory profiling and `torch.compile`
176- CUDA graph capture
177- Warmups
178- Empty DP forward passes for EP+DP
179
180MRV2 simplifies this:
181
1821. `execute_model` supports dummy runs without affecting state.
1832. `dummy_run` delegates to `execute_model` for profiling, warmup, and empty DP forward passes.
1843. CUDA graph capture uses a separate dedicated path.
185
186This reduces complexity and removes bugs caused by divergence between `execute_model` and `dummy_run` behavior.
187
188## 9. Explicit CUDA Graph Management
189
190V1's CUDA graph handling is implicit and hard to reason about. MRV2 uses a `CUDAGraphManager` that explicitly captures and launches full CUDA graphs through standard PyTorch APIs.
191
192This makes graph lifecycle and execution mode decisions more understandable and easier to extend. Example: MRV2 can capture multiple draft-model forward passes into one CUDA graph.
193
194### Fused Multi-Step Draft Decoding
195
196Autoregressive speculative decoding executes several dependent draft steps per scheduler step. In the fused path, MRV2 captures all post-prefill draft steps in one full CUDA graph instead of replaying a separate graph for each draft token. Attention metadata is built once before the loop, while common step-dependent tensors keep stable addresses and are updated in place between draft steps.
197
198Some attention backends also materialize derived state, such as scheduler metadata or sparse indices. Before opting into the fused path, these backends must implement `AttentionMetadataBuilder.update_draft_decode_metadata()` to update or invalidate that state after the draft inputs advance. The hook runs during CUDA graph capture, so only the GPU operations it issues are recorded and executed during replay; its Python body is not run again. Implementations must therefore use capture-safe operations and keep all replayed tensor state in persistent storage.
199
200For draft models that advance positions, the fused path is enabled only when every draft attention group declares `supports_draft_decode_metadata_update`. Otherwise, MRV2 falls back to rebuilding attention metadata between draft steps. Draft models that keep positions fixed do not require this update. Before enabling a backend, developers must audit all derived metadata, including state inherited from parent builders or owned by auxiliary attention backends.
201
202## Development Philosophy
203
204MRV2 changes should meet a higher code quality bar. As feature gaps with V1 are filled, features should be reconsidered from first principles in the MRV2 design context instead of quickly porting V1 behavior.
205
206A key requirement is preserving modularity and clean abstraction boundaries, even if that requires more upfront design iteration.
